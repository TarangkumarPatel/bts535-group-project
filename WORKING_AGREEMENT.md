# Working Agreement

**Project:** Privacy-First Local Agentic Knowledge Base and Code Synthesizer.

**Team:** Group 4 (Tarangkumar Patel, Jaishnav Prasad, Festus Sabu, Faith Sam).

**Course:** BTS535NAA

This agreement describes how our team works together. Every member has agreed to it, and we will revisit it at the end of each sprint.

## Communication

- Our main channel for day-to-day discussion is our group chat. All project decisions are recorded in GitHub issues so there is a written record.
- Members reply to messages within 24 hours on weekdays.
- If a member cannot attend a meeting or will miss a deadline, they tell the team as early as possible, before the deadline.
- Discussions stay respectful and focused on the work, not the person.

## Meetings

- **Sprint Planning:** at the start of each sprint, to choose the sprint goal and user stories.
- **Stand-ups:** short check-ins during the sprint covering what each member did, what they will do next, and any blockers.
- **Sprint Review and Retrospective:** at the end of each sprint, to demo completed work and agree on improvements.
- Members arrive on time and prepared. Notes and action items are added to the related issue.

## Task Management

- All work is tracked as issues on our GitHub Project board.
- Members assign issues to themselves before starting work and keep the issue's status column up to date (Backlog, Ready, In Progress, In Review, Done).
- Each sprint is a milestone, and every user story belongs to a milestone.
- If a task is blocked for more than one day, the member raises it at the next stand-up or in the group chat.

## Git and GitHub Workflow

- **No direct commits to `main`.** All changes, including documentation and README edits, go through a pull request.
- Each issue gets its own branch, named `<issue-number>-short-description` (for example, `14-update-readme`).
- Commit messages are short, clear and reference the issue number, for example `Add file ingestion endpoint (#21)`.
- Each pull request links its issue in the description (`Closes #N`) and requests at least one teammate as reviewer.
- A pull request is merged only after at least one teammate approves it. Authors do not approve their own pull requests.
- Members pull the latest `main` before starting new work and resolve merge conflicts on their own branch.
- Reviews are completed within 48 hours of being requested.

## Code Quality

- Code follows the agreed style for each language (PEP 8 for Python; ESLint and Prettier for TypeScript and React).
- Code is readable, with meaningful names and comments where the logic is not obvious.
- New features include tests where practical, and existing tests must pass before merging.
- No secrets, API keys or personal files are committed to the repository.

## Decision Making and Conflict Resolution

- Decisions are made by discussion and consensus. If we cannot agree, we take a majority vote.
- Disagreements are raised early and directly with the person involved, in a respectful way.
- If a conflict cannot be resolved within the team, we bring it to the professor.

## Accountability

- Each member completes their assigned user stories by the end of the sprint or tells the team early if they need help.
- Workload is shared fairly. Each member takes one user story per sprint.
- Members help each other when someone is stuck.

## Agreement

By contributing to this repository, each team member agrees to follow this Working Agreement.
